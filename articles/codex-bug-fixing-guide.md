# Codex 修复 Bug 怎么用？2026 从问题定位到测试验证完整实战

如果只是让 ChatGPT：

> “看看这段代码哪里有问题”

很多时候只需要复制一段代码进去就够了。

但真实开发中的 Bug 往往没有这么简单。

一个报错可能涉及：

* 多个文件
* API 调用
* 数据库
* 中间件
* 权限逻辑
* 前后端交互
* 测试环境
* 第三方依赖

这也是 **Codex** 比普通代码问答更有价值的地方之一。

Codex 可以围绕真实代码仓库：

* 阅读相关文件
* 分析调用关系
* 查找问题根因
* 修改代码
* 运行测试
* 检查代码变化
* 辅助 Code Review

但前提是：

> **不要只给它一句“帮我修 Bug”。**

真正稳定的 Codex Bug 修复流程应该是：

```text
复现问题
↓
定位范围
↓
分析根因
↓
制定修复方案
↓
最小范围修改
↓
运行测试
↓
检查 Diff
↓
再次 Review
```

下面用一个完整开发场景讲清楚。

---

## 一、Codex 为什么适合排查 Bug？

传统使用 ChatGPT 修 Bug 时，经常是：

```text
复制报错
↓
复制代码
↓
ChatGPT 猜原因
↓
自己修改
↓
继续报错
↓
再复制一段代码
```

问题在于：

> ChatGPT 看到的通常只是你主动提供的那部分上下文。

而 Codex 在项目环境中工作时，可以继续检查：

```text
相关文件
调用关系
测试
配置
Git Diff
项目规则
```

例如一个登录接口返回 500。

真正的问题可能不在：

```text
login.ts
```

而是在：

```text
middleware/auth.ts
```

或者：

```text
services/user.ts
```

甚至：

```text
database/repository.ts
```

如果只复制一个接口文件给 AI，很容易得到错误判断。

---

## 二、不要直接输入“帮我修这个 Bug”

这是很多新手最常见的使用方式：

```text
帮我修复当前项目里的 Bug。
```

问题是：

> 哪个 Bug？

Codex 不知道：

* 当前现象是什么
* 正确结果是什么
* 怎么复现
* 哪些文件不能动
* 哪些行为不能改变
* 修复完成怎么验证

因此更好的任务描述应该包含四个部分：

```text
问题
+
预期结果
+
限制条件
+
验证方式
```

---

## 三、一个比较好的 Bug Prompt

例如：

```text
当前问题：

GET /api/users/:id

当用户不存在时返回 500。

预期结果：

用户不存在时应该返回 404。

要求：

1. 先定位问题原因
2. 暂时不要修改代码
3. 不修改数据库 Schema
4. 不改变其他 API 行为
5. 找到原因后告诉我准备修改哪些文件
6. 等确认后再执行修改
```

这比：

```text
修一下 users API
```

要稳定得多。

---

# 四、第一阶段：先让 Codex 复现问题

不要看到报错以后马上修改。

第一步应该尽可能确认：

> **问题真的可以稳定复现吗？**

可以输入：

```text
先不要修改任何文件。

请检查当前项目，并尝试复现以下问题：

GET /api/users/:id

当用户不存在时，接口返回 500。

请确认：

1. 是否能够复现
2. 实际返回状态码
3. 实际错误信息
4. 问题出现在哪个执行阶段
5. 涉及哪些文件

完成后只输出分析结果。
```

这样做非常重要。

因为有些 Bug 实际上可能是：

```text
开发环境问题
配置问题
测试数据问题
数据库问题
```

而不一定真的是代码逻辑错误。

---

# 五、第二阶段：让 Codex 找“根因”，不要只找报错位置

假设 Codex 找到：

```text
users.controller.ts
```

出现异常。

不要马上让它改。

继续问：

```text
继续分析这个问题。

不要修改代码。

请从调用链向上和向下检查，确认：

1. Controller 为什么收到异常
2. Service 返回了什么
3. Repository 在用户不存在时返回什么
4. 当前错误处理逻辑在哪里
5. 为什么最终变成 500
6. 真正的根因在哪一层

不要只告诉我报错文件，要解释完整调用链。
```

这一步的目标是：

> **找到 Root Cause，而不是找到 Error Location。**

两者完全不同。

---

## 六、什么叫“报错位置”和“真正根因”？

例如：

```text
Controller
↓
调用 UserService
↓
调用 UserRepository
↓
findById 返回 null
↓
Service 直接访问 user.name
↓
TypeError
↓
全局异常处理返回 500
```

最终看到报错的位置可能是：

```text
user.service.ts
```

但真正的问题是：

> 没有正确处理“用户不存在”的业务情况。

正确修复不一定是：

```text
try {
...
} catch {}
```

而更可能是：

```text
if (!user) {
    throw new NotFoundError(...)
}
```

所以定位 Bug 时，最重要的不是：

> “哪一行报错？”

而是：

> **为什么程序会进入这个错误状态？**

---

# 七、第三阶段：让 Codex 先给修复方案

找到原因以后，也不要马上执行。

可以输入：

```text
基于刚才找到的根因，给出最小修复方案。

暂时不要修改代码。

请说明：

1. 准备修改哪些文件
2. 每个文件为什么要改
3. 是否需要新增测试
4. 是否会影响现有 API
5. 是否存在兼容性风险
6. 是否有更小的修复方式

优先选择修改范围最小的方案。
```

这里有一个非常重要的关键词：

> **最小修复（minimal fix）**

修一个 Bug，通常不要顺便：

```text
重构整个模块
+
升级依赖
+
修改目录
+
重新设计 API
```

否则以后出了问题，很难判断到底是哪一次修改导致的。

---

# 八、第四阶段：确认后再让 Codex 修改

如果方案合理，再执行：

```text
按照刚才的最小修复方案执行。

要求：

1. 只修改必要文件
2. 不做无关重构
3. 保持现有代码风格
4. 不改变数据库结构
5. 不改变其他 API 返回行为
6. 修改完成后先暂停，不要继续扩展任务
```

这种方式非常适合真实项目。

---

# 九、第五阶段：一定要补测试

修 Bug 最怕的是：

```text
现在好了
```

但是：

```text
下周又坏了
```

所以修复之后，应该至少添加一个：

> **回归测试（Regression Test）**

例如当前问题是：

```text
用户不存在时返回 500
```

那测试至少应该覆盖：

```text
用户存在
→ 200

用户不存在
→ 404
```

可以让 Codex：

```text
针对刚才修复的问题补充测试。

至少覆盖：

1. 用户存在时正常返回
2. 用户不存在时返回 404
3. 不影响现有正常场景

尽量沿用项目已有测试结构和测试框架。
```

---

# 十、为什么修 Bug 必须有 Regression Test？

因为测试的作用不仅是证明：

> **现在修好了。**

更重要的是防止未来：

```text
新的修改
↓
又把同一个 Bug 引回来
```

这也是为什么真实软件工程中：

```text
Bug Fix
```

最好同时伴随：

```text
Regression Test
```

---

# 十一、第六阶段：运行相关测试，而不是只看代码

代码看起来正确：

```text
≠
```

代码真的正确。

修改完成以后，可以让 Codex：

```text
运行与当前修改最相关的测试。

如果存在：

- 单元测试
- API 测试
- 集成测试

优先运行相关测试。

如果测试失败：

不要隐藏失败，
不要继续大范围修改，
先告诉我失败原因。
```

这一点非常重要。

不要让 AI：

```text
测试失败
↓
继续不断自动修改
↓
改越来越多
```

更稳定的方式是：

```text
测试失败
↓
暂停
↓
分析
↓
确认原因
↓
再修改
```

---

# 十二、第七阶段：检查 git diff

即使所有测试通过，也不要马上提交。

建议检查：

```bash
git diff
```

重点看：

* 修改了哪些文件
* 有没有改无关代码
* 有没有删除重要逻辑
* 是否改变 API 行为
* 是否出现大面积格式变化
* 是否加入不必要依赖

还可以让 Codex：

```text
检查当前 git diff。

不要修改代码。

请告诉我：

1. 一共修改了哪些文件
2. 每个文件修改目的
3. 是否存在无关修改
4. 是否有可能影响旧功能
5. 是否存在遗漏
6. 当前修改是否符合“最小修复”原则
```

---

# 十三、第八阶段：再做一次 Code Review

最后再执行一次 Review。

可以输入：

```text
对当前 Bug Fix 做最终 Code Review。

不要修改代码。

重点检查：

1. Root Cause 是否真正解决
2. 是否只是掩盖异常
3. 是否可能产生新的边界问题
4. 是否影响其他 API
5. Regression Test 是否充分
6. 异常处理是否合理
7. 有没有安全风险
8. 有没有不必要的复杂度

按照：

高风险
中风险
低风险

输出结果。
```

如果使用 Codex CLI，也可以结合：

```text
/review
```

进行代码检查。

# 十四、完整 Bug 修复工作流

可以直接记住这一套：

```text
发现 Bug
↓
建立 Git 检查点
↓
描述问题
↓
让 Codex 复现
↓
分析调用链
↓

↓
给出最小修复方案
↓
人工确认

↓
Code Review

```

这套流程比：

```text
Codex，帮我修这个 Bug
```

靠谱很多。

# 十五、实战案例：登录接口返回 500

下面看一个完整例子。

假设：

```text
POST /api/login
```

错误密码时，本来应该返回：

```text
401 Unauthorized
```

但现在返回：

```text
500 Internal Server Error
```

---

## 第一步：描述问题

```text
当前存在一个登录 Bug。

接口：

POST /api/login

复现方式：

1. 输入存在的邮箱
2. 输入错误密码
3. 提交登录

当前结果：

500 Internal Server Error

预期结果：

401 Unauthorized

先不要修改代码。

请复现问题并分析完整调用链。
```

---

## 第二步：分析根因

假设 Codex 分析后发现：

```text
login.controller
↓
auth.service
↓
password.compare
↓
返回 false
↓
代码没有处理 false
↓
继续读取不存在的 session
↓
产生异常
↓
500
```

这时候就可以确认：

> 真正问题是错误密码分支没有正确退出。

---

## 第三步：要求最小修复

```text
根据刚才分析，给出最小修复方案。

目标：

错误密码返回 401。

要求：

- 不改变成功登录逻辑
- 不修改数据库
- 不升级依赖
- 不改变 Token 格式
- 修改范围尽量小
- 增加回归测试

先给方案，不修改。
```

---

## 第四步：执行

确认后：

```text
执行刚才方案。

完成后：

1. 列出修改文件
2. 运行相关测试
3. 告诉我测试结果
4. 不要做任何无关重构
```

---

# 十六、哪些 Bug 特别适合 Codex？

Codex 很适合处理：

### 1. API 错误

例如：

```text
返回错误状态码
参数校验异常
异常处理错误
接口字段缺失
```

---

### 2. 前端 Bug

例如：

```text
组件不更新
状态不同步
按钮无响应
表单异常
页面报错
```

---

### 3. TypeScript 类型问题

例如：

```text
类型冲突
undefined
null
泛型问题
接口类型不一致
```

---

### 4. 测试失败

例如：

```text
unit test failure
integration test failure
CI failure
```

---

### 5. 依赖升级后的兼容问题

例如：

```text
API 改变
配置变化
旧代码失效
```

---

### 6. 多文件逻辑问题

这类 Bug 通常是 Codex 相比普通聊天式代码问答更有优势的场景。

---

# 十七、哪些 Bug 不适合直接让 Codex 自动修改？

一些高风险场景应该更加谨慎。

例如：

### 数据库生产事故

```text
线上数据错误
大量数据丢失
Migration 异常
```

---

### 支付系统

```text
金额计算
退款
支付回调
订单状态
```

---

### 权限和认证

```text
用户权限
管理员权限
Token
身份验证
```

---

### 安全漏洞

```text
SQL Injection
权限绕过
敏感数据泄露
```

这些场景可以让 Codex：

```text
分析
定位
给方案
补测试
```

但最终修改应该进行更加严格的人工 Review。

---

# 十八、不要让 Codex 为了“测试通过”修改测试

这是一个很重要的原则。

如果：

```text
代码有 Bug
↓
测试失败
```

错误的做法可能是：

```text
修改测试
↓
让测试变绿
```

但 Bug 仍然存在。

因此最好在 AGENTS.md 中加入：

```markdown
## Testing Rules

- 不要为了让测试通过而降低测试要求
- 不要删除失败测试
- 不要跳过已有测试
- 如果认为测试本身错误，先解释原因再修改
```

这样可以避免很多问题。

---

# 十九、不要轻易删除“看起来没用”的代码

修 Bug 时，Codex 可能发现：

```text
某段逻辑似乎没有使用
```

但真实项目中它可能通过：

* 动态调用
* Reflection
* 配置
* Plugin
* Runtime
* 外部服务

被使用。

所以可以加入约束：

```text
不要删除与当前 Bug 无直接关系的代码。

如果认为某段代码可以删除，
先说明证据和影响，
等待确认后再操作。
```

---

# 二十、不要一次让 Codex 修 10 个 Bug

如果 Issue 中有：

```text
Bug 1
Bug 2
Bug 3
Bug 4
Bug 5
```

最好拆开。

推荐：

```text
Bug 1
↓
修复
↓
测试
↓
Commit

Bug 2
↓
修复
↓
测试
↓
Commit
```

这样即使某一步出问题，也容易：

```text
定位
回滚
Review
```

---

# 二十一、Bug 修复前先建立 Git 检查点

建议在开始前：

```bash
git status
```

确认工作区。

如果已有人工修改，先处理好。

必要时建立：

```bash
git add .
git commit -m "checkpoint before bug fix"
```

这样 Codex 后面的修改会非常清楚。

# 二十二、一个通用 Bug 修复 Prompt 模板

以后遇到任何 Bug，都可以先复制下面这套：

```text
请帮助分析当前 Bug。

问题：

【描述当前现象】

复现步骤：

1.
2.
3.

当前结果：

【实际结果】

预期结果：

【正确结果】

要求：

1. 先复现问题
2. 暂时不要修改代码
3. 找到完整调用链
4. 确定真正 Root Cause
5. 告诉我涉及哪些文件
6. 给出最小修复方案
7. 不修改无关代码
8. 不升级无关依赖
9. 不改变数据库结构
10. 等我确认后再执行

最后输出：

- 是否成功复现
- 根因
- 涉及文件
- 修复方案
- 潜在风险
```

这个 Prompt 基本可以作为：

> **Codex Bug 排查通用模板。**

# 二十三、修改阶段 Prompt

确认分析以后可以继续：

```text
执行刚才的最小修复方案。

要求：

1. 只修改必要文件
2. 保持现有代码风格
3. 不做无关重构
4. 增加 Regression Test
5. 运行相关测试
6. 测试失败立即说明
7. 完成后总结修改内容
8. 不自动 Commit
```

# 二十四、最终 Review Prompt

修改结束以后：

```text
对当前 Bug Fix 做最终检查。

不要继续修改。

检查：

1. Root Cause 是否真正解决
2. 是否存在新的 Bug
3. 是否影响其他功能
4. 是否存在安全问题
5. 测试是否充分
6. 是否存在无关修改
7. 是否符合最小修改原则

最后告诉我：

是否建议 Commit。

如果不建议，请说明原因。
```

# 二十五、Codex 修 Bug 最重要的不是“自动”

很多人使用 AI Coding Agent 的目标是：

```text
全自动修 Bug
```

但对于真实项目，更重要的是：

> **可验证。**

好的 AI 开发流程应该是：

```text
AI 做更多执行
+
开发者控制目标
+
测试验证结果
+
Git 保留修改记录
+
最终人工确认
```

而不是：

```text
AI 说修好了
↓
直接上线
```

# 二十七、总结

Codex 修复 Bug 的正确用法，并不是：

```text
“帮我修一下”
```

而应该是：

```text
描述问题
↓
复现
↓
定位
↓
找到 Root Cause
↓
制定最小方案
↓
执行修改
↓
增加 Regression Test
↓
运行测试
↓
检查 Diff
↓
最终 Review
```

如果只记住三个原则：

> **先分析，再修改。**

> **修改范围越小越好。**

> **没有测试验证，就不要轻易认为 Bug 已经修好。**

当这套流程逐渐熟悉以后，Codex 才会真正从：

> “帮我写代码的 AI”

变成：

> **参与真实软件工程流程的 Coding Agent。**
