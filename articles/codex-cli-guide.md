# Codex CLI 怎么用？2026 从安装到实际项目操作完整教程

如果你已经了解 Codex 是什么，下一步非常值得熟悉的就是 **Codex CLI**。

相比只在网页中和 AI 对话，Codex CLI 可以直接运行在终端中，并结合当前项目的文件、Git 状态、开发命令和代码上下文完成任务。

简单理解：

> **Codex CLI = 可以直接在终端里和你的真实代码项目一起工作的 AI Coding Agent。**

它比较适合：

* 阅读陌生代码仓库
* 分析项目结构
* 查找 Bug
* 修改多个文件
* 运行测试
* 重构代码
* 检查 Git Diff
* Code Review
* 自动化重复开发任务

下面从安装开始，完整介绍 Codex CLI 的基本使用方式。

---

## 一、Codex CLI 是什么？

Codex CLI 是 OpenAI Codex 的终端使用方式。

安装后，可以直接进入自己的项目目录运行：

```bash
codex
```

之后就可以在终端中给 Codex 描述任务。

例如：

```text
先阅读当前项目。

不要修改任何文件。

告诉我：

1. 项目使用什么技术栈
2. 入口文件在哪里
3. 主要目录分别负责什么
4. 核心业务模块有哪些
5. 建议我优先阅读哪些文件
```

Codex 会结合当前代码仓库进行分析。

这与单纯把几段代码复制到 ChatGPT 中最大的区别在于：

**Codex CLI 可以围绕整个项目上下文工作。**

---

## 二、Codex CLI 怎么安装？

目前比较方便的方法之一是通过 npm 安装。

如果电脑已经安装 Node.js / npm，可以执行：

```bash
npm install -g @openai/codex
```

安装完成后检查：

```bash
codex
```

如果能够正常进入 Codex CLI，说明安装基本完成。

macOS / Linux 用户也可以按照当前官方提供的安装方式进行安装。

安装完成以后，后续更新 Codex CLI 时建议关注官方版本变化，不要长期使用过旧版本。

---

## 三、第一次启动 Codex CLI

先进入自己的项目目录。

例如：

```bash
cd my-project
```

然后运行：

```bash
codex
```

首次运行时，按照界面提示完成登录。

登录完成以后，Codex 会以当前项目目录作为主要工作上下文。

所以不要随便在：

```text
C:\
```

或者：

```text
/
```

这种非常大的目录直接启动。

更推荐：

```text
my-project/
├── src/
├── public/
├── tests/
├── package.json
├── README.md
└── ...
```

进入：

```bash
cd my-project
```

之后再运行：

```bash
codex
```

这样 Codex 的工作范围会更加清晰。

---

## 四、新手第一次不要让 Codex 直接改代码

刚开始使用时，我比较推荐先让 Codex **只读项目**。

输入：

```text
阅读当前项目。

暂时不要修改任何文件。

先分析：

1. 项目技术栈
2. 目录结构
3. 项目入口
4. 核心模块
5. 主要依赖
6. 可能需要特别注意的代码
```

这个步骤非常重要。

因为你可以先观察：

> Codex 是否真的理解了你的项目。

如果第一步理解都出现明显错误，就不要马上让它大规模修改。

## 五、Codex CLI 常用命令

Codex CLI 中有一些非常值得了解的命令。

### 1. `/status`

查看当前会话配置。

```text
/status
```

刚开始使用时，如果不确定当前状态，可以先查看一下。

---

### 2. `/model`

用于查看或调整当前可使用的模型以及相关推理设置。

```text
/model
```

不同任务对模型能力的要求并不完全相同。

例如：

简单解释代码：

```text
解释这个函数的作用
```

和：

```text
分析这个大型项目的权限系统，
找出可能存在的逻辑问题，
同时检查相关测试。
```

复杂度明显不同。

所以不要只关注“模型名字”，还应该根据任务难度调整工作方式。

---

### 3. `/permissions`

这个命令非常重要。

```text
/permissions
```

它主要用于控制 Codex 在当前任务中能够执行哪些操作。

例如：

* 是否可以修改文件
* 是否可以运行命令
* 哪些操作需要确认

对于刚开始使用 Codex CLI 的用户，不建议什么权限都直接放开。

**先观察，再逐渐增加权限。**

---

### 4. `/review`

可以用来检查当前代码变更。

```text
/review
```

例如你刚刚让 Codex 修改了一批代码，可以再让它检查：

```text
检查刚才的所有修改。

重点关注：

1. 有没有明显 Bug
2. 是否影响原有功能
3. 是否遗漏异常处理
4. 是否需要补充测试
5. 有没有不必要的代码修改
```

这一步非常适合在 Commit 之前进行。

---

### 5. `/init`

可以用于为项目创建 Codex 使用的项目说明文件。

```text
/init
```

如果你准备长期在一个项目中使用 Codex，这一步值得进一步研究。

尤其是后面我们会单独讲到的：

```text
AGENTS.md
```

可以用来告诉 Coding Agent：

* 项目规则
* 编码规范
* 哪些文件不能修改
* 测试要求
* 构建命令
* 项目约束

这对大型项目尤其重要。

---

## 六、用 Codex CLI 阅读陌生项目

这是我非常推荐的使用场景。

进入项目后输入：

```text
先不要修改代码。

完整了解这个项目后回答：

1. 这个项目解决什么问题？
2. 使用什么技术栈？
3. 项目从哪里启动？
4. src 下面主要目录分别负责什么？
5. 数据是怎么流动的？
6. API 在哪里定义？
7. 哪些文件最值得优先阅读？
```

接下来还可以继续：

```text
重点分析用户登录模块。

告诉我：

1. 登录入口
2. 身份验证流程
3. Token 在哪里处理
4. 权限在哪里检查
5. 哪些文件与登录功能直接相关

仍然不要修改代码。
```

这比一开始：

```text
优化这个项目
```

更加稳定。

---

## 七、使用 Codex CLI 修复 Bug

假设项目出现：

```text
用户不存在时，
GET /api/users/:id
返回 500
```

不要只输入：

```text
修复这个 Bug
```

推荐这样写：

```text
检查 GET /api/users/:id。

目前的问题是：

当用户不存在时接口返回 500。

预期行为：

应该返回 404。

要求：

1. 先找到错误原因
2. 不修改数据库 Schema
3. 不改变其他 API 行为
4. 修改范围尽量小
5. 修改完成后运行相关测试
6. 最后列出修改的文件
```

这种任务描述非常适合 Codex。

因为：

**问题、目标、限制、验证方式都非常明确。**

---

## 八、先计划，再让 Codex 修改

对于稍微复杂一点的任务，不建议直接让 Codex开工。

例如你准备重构登录系统。

可以先输入：

```text
分析当前登录模块。

先不要修改代码。

告诉我：

1. 当前实现方式
2. 存在哪些问题
3. 哪些问题最值得优先解决
4. 如果重构，需要修改哪些文件
5. 可能带来哪些风险
```

然后：

```text
根据刚才的分析制定一个重构计划。

暂时仍然不要修改代码。

按照步骤列出修改顺序。
```

确认方案合理以后再说：

```text
执行第 1 步。

只完成第 1 步。

完成以后暂停，告诉我修改了什么。
```

然后再继续第 2 步。

对于比较重要的项目，这种方式比“一次全部修改”更容易控制。

---

## 九、每次大型修改之前先建立 Git 检查点

这是使用 Codex CLI 时非常重要的习惯。

在开始任务前，可以先检查：

```bash
git status
```

确认目前工作区状态。

如果当前修改已经确认没有问题，可以先 Commit：

```bash
git add .
git commit -m "checkpoint before codex changes"
```

然后再让 Codex开始处理新任务。

这样即使修改结果不理想，也更容易：

```text
比较修改
恢复代码
定位问题
```

特别是刚开始使用 Codex CLI 时，不建议让大量未提交的人工修改和 AI 修改全部混在一起。

---

## 十、修改完成后一定检查 Diff

不要因为 Codex 显示：

```text
Task completed
```

就认为一定完成了。

至少还应该检查：

```bash
git diff
```

重点看：

* 修改了哪些文件
* 有没有修改不应该动的地方
* 是否删除了重要代码
* 是否改变接口行为
* 有没有多余修改

还可以让 Codex自己先做一次检查：

```text
重新检查你刚才做的全部修改。

不要继续修改。

只告诉我：

1. 修改了哪些文件
2. 每个文件为什么要修改
3. 有没有可能产生兼容性问题
4. 有没有遗漏测试
5. 有没有你自己不确定的修改
```

这一步非常值得养成习惯。

---

## 十一、用 Codex CLI 做 Code Review

Codex CLI 不只是能写代码，也很适合做代码检查。

例如：

```text
检查当前未提交的修改。

不要修改代码。

重点寻找：

1. 逻辑 Bug
2. 空值问题
3. 异常处理遗漏
4. 安全风险
5. 重复代码
6. 性能问题
7. 缺少测试的地方

按照严重程度排序。
```

或者使用：

```text
/review
```

进行专门的代码检查。

特别是在：

```text
git commit
```

之前做一次 Review，通常比修改完成马上提交更稳妥。

---

## 十二、Codex CLI 怎么恢复之前的会话？

如果之前已经用 Codex分析过一个项目，不一定每次都需要从头开始。

可以使用：

```bash
codex resume
```

恢复之前的会话。

这种方式比较适合：

```text
第一天
分析项目
↓
第二天
继续处理 Bug
↓
第三天
继续进行重构
```

避免每次重新解释所有上下文。

---

## 十三、Codex CLI 还能加入图片上下文

有些问题仅靠文字描述并不好解释。

例如：

* 页面 UI 问题
* 报错截图
* 设计稿
* 架构图

Codex CLI 当前也支持把图片作为上下文加入任务。

这类能力对于前端开发尤其有用。

例如：

```text
参考这个页面截图。

检查当前前端项目。

找出为什么页面布局和设计稿存在明显差异。

先分析，不要修改。
```

然后再逐步处理具体问题。

---

## 十四、需要最新资料时可以使用搜索能力

有些开发问题依赖最新信息。

例如：

```text
某个框架最新版 API
```

或者：

```text
刚发布的新版本是否改变了配置方式
```

Codex CLI 也可以在适合的场景使用搜索能力来获取当前上下文。

不过对于项目代码问题，优先级仍然应该是：

```text
先理解本地项目
↓
确认版本
↓
再查对应资料
```

否则很容易把其他版本的解决方法直接套到当前项目。

---

## 十五、Codex CLI 自动化：codex exec

当熟悉交互式使用以后，还可以进一步了解：

```bash
codex exec
```

它更适合：

* 自动化脚本
* CI/CD
* 固定开发流程
* 重复任务

例如一些团队可能希望自动完成：

```text
检查代码
↓
运行固定分析
↓
输出结果
```

这种场景就可以继续研究非交互式 Codex 工作流。

不过新手不用一开始就研究自动化。

推荐先把：

```text
codex
```

交互模式熟练以后，再学习：

```text
codex exec
```

## 十六、新手最容易犯的 5 个错误

### 1. 任务太宽

例如：

```text
优化整个项目
```

范围太大。

---

### 2. 不给限制条件

例如没有告诉 Codex：

```text
不要修改数据库
不要修改 API
不要升级依赖
```

很容易导致修改范围超出预期。

---

### 3. 不检查 Diff

AI修改完成以后直接 Commit，是不推荐的。

---

### 4. 一次修改太多

10 个问题最好不要一次全部处理。

先：

```text
问题 1
↓
验证
↓
问题 2
↓
验证
```

更加容易定位问题。

---

### 5. 没有 Git 检查点

大型修改之前不 Commit，出现问题以后恢复起来会比较麻烦。

---

## 十七、推荐的 Codex CLI 工作流程

如果你刚开始使用，可以直接照这个流程：

```text
进入项目目录
↓
git status
↓
建立 Git 检查点
↓
运行 codex
↓
让 Codex 阅读项目
↓
只分析，不修改
↓
制定修改方案
↓
执行一个小任务
↓
运行测试
↓
检查 git diff
↓
使用 /review
↓
人工确认
↓
Commit
```

这个流程看起来比：

```text
让 AI 自动全部完成
```

慢一点。

但对于真实开发来说，通常更加容易控制。

## 十八、一个可以直接复制的 Codex CLI Prompt

第一次进入项目，可以直接使用：

```text
请先完整阅读当前项目。

暂时不要修改任何文件，也不要执行破坏性操作。

请完成以下分析：

1. 判断项目使用的技术栈
2. 找到项目入口
3. 解释主要目录用途
4. 找出核心业务模块
5. 找出测试相关目录
6. 找出构建和运行命令
7. 找出可能存在的项目说明文件
8. 告诉我最值得优先阅读的 10 个文件

最后用简洁的方式说明这个项目整体是怎么运行的。
```

完成以后再继续：

```text
现在只分析当前项目可能存在的问题。

不要修改代码。

按照：

高优先级
中优先级
低优先级

分类输出。
```

这种方式非常适合第一次接触 Codex CLI。

## 二十、总结

Codex CLI 真正值得学习的地方，并不是简单地：

> 在终端里面和 AI 聊天。

而是让 Coding Agent 真正进入开发流程：

```text
理解项目
↓
分析任务
↓
制定方案
↓
修改代码
↓
运行命令
↓
执行测试
↓
检查 Diff
↓
Code Review
```

对于刚开始使用的人，最推荐的原则仍然是：

> **先分析，小范围修改，每一步都验证。**

不要一开始追求“AI 自动完成整个项目”。

当你逐渐熟悉：

* Codex CLI
* Git
* `/permissions`
* `/review`
* AGENTS.md
* 测试流程

以后，再慢慢增加 Codex 能够独立完成的任务范围。

这样通常更适合真实开发项目。
